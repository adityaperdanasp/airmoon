# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`airmoon` is a Muslim app: Qur'an reader, prayer times, mosque electricity donation routed directly to a PLN customer ID (not a committee bank account), plus lighter utility features (zakat calculator, Hijri calendar, asmaul husna, daily duas, mosque finder, Makkah live, greeting cards).

This repo is deliberately just the buildable product surface — app code, design references, and Firebase config. Business/reference material (pitch decks, financial models, market research) lives outside this repo and is intentionally not published here.

**`app/` is the real, deployed product.** `mockup/` and `design-canvas/` are design artifacts that came before it — kept as reference for visual language and for prototyping new screens before building them for real, not as things to deploy.

## Structure & how to run things

- **`app/`** — the real app: React + Vite. Deployed to **both** Firebase Hosting (https://airmoon-d9620.web.app) and Vercel (https://airmoon.vercel.app) — same static frontend, two hosts. **Redeploy both after every change that should go live** — `git push` auto-deploys Vercel, but Firebase Hosting needs its own explicit `firebase deploy --only hosting` from the repo root; they will silently drift apart otherwise (this has actually happened mid-session before — caught by comparing the live `/assets/*.js` hash against the local `app/dist` one). Vercel also carries the serverless functions Firebase Hosting can't run: `app/api/ask-me.js`, `api/nearby-mosques.js`, `api/aladhan.js`, `api/send-prayer-notifications.js`.
  ```
  cd app && npm install   # first time only
  npm run dev             # local dev server
  npm run build            # production build → app/dist
  ```
  Deploy after a `build`:
  ```
  firebase deploy --only hosting   # from repo root — firebase.json's hosting.public points at app/dist
  vercel --prod                    # from repo root (not app/!) — see the Vercel section below for why
  ```
  Do both when `app/` changes — they're independent deploys, not automatically in sync. The Vercel project is also Git-connected, so a `git push` to `main` triggers its own auto-deploy on top of any manual `vercel --prod` you run — expect two deployments per push, both landing on the same production alias.

  Routing is client-side (`react-router-dom`, `BrowserRouter`) — both `firebase.json` and `app/vercel.json` have a catch-all rewrite to `index.html` so deep links work on either host.

- **`mockup/`** — the original static HTML/CSS home-screen prototype. No longer deployed (superseded by `app/`); kept for history. If you open it, do so through a local server (`cd mockup && python3 -m http.server 8743`), not `file://` — it fetches Google Fonts and uses a same-origin stylesheet link.

- **`design-canvas/`** — source for the editable Claude Design canvas (`Main.dc.html`, `Login.dc.html`, `SurahReader.dc.html`, etc. — one `.dc.html` per screen, plus `canvas.json` for layout). Authored through the `design` skill (invoke `/design`), not hand-edited after seeding. Useful for prototyping a new screen's look before building it for real in `app/`; the two are not kept in lockstep automatically — a design change here doesn't propagate to `app/` on its own. `airmoon-home.html` is the seeded/published output — never edit it directly.

## App architecture (`app/src/`)

- **`context/`** — `AuthProvider` (Firebase Auth state + sign-up/in/out), `ThemeProvider` (light/dark, persisted to `localStorage`, toggles `data-theme` on `<html>`), `LangProvider` (id/en, persisted, `t(key)` lookup against `lib/translations.js`).
- **`lib/firebase.js`** — Firebase SDK init. Config is duplicated from `../../firebase-config.js` at the repo root (client config, not a secret) — keep both in sync if it ever changes.
- **`lib/quranApi.js`** — EQuran.id v2 (`equran.id/api/v2`), public, no key. Surah list + detail + per-ayat audio for 5 reciters.
- **`lib/prayerApi.js` / `lib/usePrayerTimes.js`** — real `navigator.geolocation` + Aladhan API (`method=20`, Kemenag) for prayer times; the hook also derives the next prayer + a live countdown. Reused by both Home's widget and the full Jadwal Sholat page.
- **`lib/mosqueApi.js`** — tries Google Places API (New) first, via the Vercel function `api/nearby-mosques.js` (real ratings/names/hours, needs `GOOGLE_MAPS_API_KEY` in Vercel — same "not set yet" situation as `ANTHROPIC_API_KEY`, see below), and falls back to OpenStreetMap Overpass (free, no key, sparser data) if that call fails for any reason. `CariMasjid.jsx` shows a small banner when it's running on the OSM fallback so it's obvious which source is live. Directions are a plain `google.com/maps/dir` deep link either way — no key needed for that part, and no plan to add the Routes API on top of it.
- **`lib/donations.js`** — Firestore-backed donation campaigns (`donations/{id}`). `watchActiveDonations()` is a live query on `status == 'active'`. No client-side write path at all anymore (see the "Daftarkan Masjid" and "Donasi payment flow" notes below for how campaigns get created and how `collected` gets credited now — both server-side, via the Admin SDK).
- **`lib/zakat.js`** — pure zakat math (penghasilan/maal/fitrah), no external dependency.
- **`data/asmaulHusna.js`** — static content, hand-authored. Low-risk, well-known text, but still **verify against a mu'tabar source (e.g. Kemenag, Hisnul Muslim) before treating as final** — not pulled from a verified API, needs a human check.
- **`data/doaHarian.js`** — `dzikirPagi` (19 items) and `dzikirPetang` (18 items) were transcribed programmatically from bekalislam.online/dzikir-doa's own per-item HTML fragments (a Syaikh Abdur Razzaq-curated selection, published by Ustadz Firanda Andirja's site) rather than typed from memory, specifically to avoid transcription errors — see the file's own header comment for the two source data-quality issues found and fixed along the way (a mislabeled title, one item's transliteration field having explanatory prose mixed in). `doaKegiatan` (3 items) is the original hand-authored content, still unverified. All of it still needs a human check against a mu'tabar reference before being treated as final — programmatic transcription avoids typos, not doctrinal review. `DoaHarian.jsx` renders these as category tabs (`doaCategories`), not a flat list.
- **`lib/quotesApi.js` / `data/quoteRefs.js`** — the "100 kutipan" on `pages/KutipanInspirasi.jsx`. Fully real: `quoteRefs.js` is just 100 valid `{surah, ayat}` coordinates (opening ayat of surahs 15–114 — picked for guaranteed validity, not curated for content), and `quotesApi.js` fetches the actual Arabic + Indonesian (Kemenag) + English (Sahih International) text live from `api.quran.com/v4`. One is shown per day (`todaysQuoteIndex()`, day-of-year mod 100), language follows `LangProvider`. No hand-typed quote text anywhere in this feature.
- **`api/aladhan.js`** — Vercel serverless function proxying both Aladhan endpoints this app uses (`?type=timings`, `?type=hijri-calendar`). Exists because api.aladhan.com's IPv6 endpoint hangs/times out on every attempt (verified with `curl -6` vs `-4`: IPv6 never connects, IPv4 is instant) — calling it directly from the browser breaks for anyone on an IPv6-preferring network (common on Indonesian mobile carriers), which is a real production bug this was found fixing, not a hypothetical. `lib/prayerApi.js` and `pages/KalenderHijriah.jsx` both go through this now instead of `api.aladhan.com` directly. No API key needed, Aladhan is free/public.
- **`api/ask-me.js`** — Vercel serverless function proxying to Claude Haiku (`claude-haiku-4-5-20251001`) for the "Ust. Rewin" chat (`pages/AskMe.jsx`, linked from Home's search bar). System prompt guardrails it to Islam-related topics only, plain-text-only replies (chat bubble doesn't render markdown), streamed response (forwards Anthropic's SSE text deltas as they arrive rather than buffering the whole reply). **`ANTHROPIC_API_KEY` is set in Vercel and confirmed working** (verified live via curl 2026-08-25). The frontend calls the fixed absolute URL `https://airmoon.vercel.app/api/ask-me`, not a relative path — that's deliberate, so it works the same whether the page is loaded from the Firebase or the Vercel host.

## Known gaps (don't assume these are done)

- **Mushaf mode — real Madani Mushaf page layout, not an approximation.** `pages/MushafReader.jsx` (route `/quran/mushaf/:page`, entry point on `SurahList.jsx`) renders actual 604-page Mushaf pagination using Quran.com's public API (`lib/mushafApi.js`, `verses/by_page/{n}?words=true` — free, no key). Two things make this authentic rather than a lookalike: (1) real page/line breaks per word (`line_number`/`page_number`), not a guessed reflow, verified against the reference screenshots that prompted this (halaman 293 = Al-Isra ending mid-page into Al-Kahf's banner + Bismillah, exact match); (2) actual King Fahd Complex (QCF) glyph fonts for the ayah text — the `code_v1` word field (not `text`, whose default encoding was found to shift depending on which other `word_fields` are requested in the same call — confirmed by testing side by side, don't trust it) gives the private-use glyph code for each word, rendered with the matching per-page font. Fonts are self-hosted at `public/fonts/mushaf/QCF_P001.woff2`–`QCF_P604.woff2` (~47MB total, one small file fetched lazily per page visited, not bulk-loaded) rather than hotlinked from `raw.githubusercontent.com/nuqayah/qpc-fonts` — that host sends `Content-Security-Policy: default-src 'none'; sandbox` on every file it serves, which some browsers apply to the font resource itself and silently reject (tofu glyphs, no console error); reproduced consistently before self-hosting fixed it. Font is free-to-use/redistribute under KFGQPC's license (no sale, no modification) — standard terms under which most Quran apps ship these exact files. `MushafLine` measures and shrinks its own font-size per line (down to a floor) since a real Mushaf line can't wrap and different screen widths will overflow a fixed size — the shrink loop explicitly re-triggers once the real per-page font is confirmed loaded via the Font Loading API (`FontFace().load()`), not just on mount, because `font-display: swap` means an early measurement pass can settle against the *fallback* font's metrics and then overflow again the moment the real font swaps in. Bismillah banner text still uses the earlier `text_uthmani` (real Unicode) + Amiri rendering, not the QCF glyph system — it's a secondary decorative element, not the primary reading text, and finding the correct standalone-Bismillah encoding for the separate `QCF_BSML` font wasn't resolved. Tajwid color-coding and per-word Indonesian gloss were researched as feasible next additions (Quran.com's `text_uthmani_tajweed` and `?words=true&language=id` respectively, both confirmed live) but not built — user picked Mushaf mode as the first of the three to ship.
  - **Last-read bookmarks are per-mode, not shared, and deliberately manual.** `users/{uid}.lastReadAyat` (renamed from the older `lastRead` — `SurahList.jsx` still falls back to reading `lastRead` for anyone who bookmarked before the rename) and `users/{uid}.lastReadMushaf` are two independent fields; switching modes never converts one into the other, matching the founder's own reasoning: someone might read in Mushaf mode one session and Ayat mode the next specifically because they got bored of one and want the other, not because they want to be forced back to an equivalent position. `SurahList.jsx` shows up to two separate "Lanjut Baca" cards. Both are set by an explicit tap (the bookmark icon in `SurahReader.jsx`, the ayah-number circle in `MushafReader.jsx`), never auto-saved on page view — auto-saving "this page" in Mushaf mode specifically doesn't work because one Mushaf page holds a dozen-plus ayat, so knowing the page alone doesn't say how far into it the reader actually got; the bookmark has to be per-ayah. Tapping a Mushaf ayah-mark writes `{ page, chapterId, chapterName, verseKey, verseNumber }`; opening `/quran/mushaf/:page?ayat=<verseKey>` (only reachable via that Lanjut Baca card) scrolls that exact ayah into view and gives it a temporary highlight ring so it's clear you're resuming, not just landing on a random spot on the page.
  - **Tajwid mode and Night Mode — the two toggles in `MushafReader.jsx`'s topbar (Night Mode also in `SurahReader.jsx`'s).** Per the founder's own framing when scoping these: reading Qur'an is "4 opsi" (Mode Ayat, Mode Mushaf Madinah, Mode Mushaf Madinah + Tajwid, Mode Night Mode) rather than tajwid/night being bolted onto Mushaf mode alone as an afterthought.
    - **Tajwid**: per-word `text_uthmani_tajweed` (added to `fetchMushafPage`'s `word_fields`) gives real Unicode text with `<rule class=X>...</rule>` markup — colored per `TAJWEED_COLORS` in `lib/mushafApi.js`, matching the published legend at alquran.cloud/tajweed-guide for this exact rule taxonomy (confirmed against the full set of 18 rule classes that actually appear, by scanning real Mushaf pages, not just the handful visible in Al-Fatihah). `parseTajweedHtml()` is a stack-based parser, not a flat regex — `<rule>` tags genuinely nest (e.g. a `custom-alef-maksora` sub-rule inside a `madda_normal` one; found the same way, by scanning broadly rather than trusting the first working case) and a non-nested regex leaves the outer `</rule>` unmatched, leaking raw tag markup as visible on-page text. Verified with an actual full-Mushaf sweep (all 604 pages, not a sample) confirming zero stray `<`/`>` survive parsing anywhere. Tajwid mode necessarily drops the QCF glyph fonts entirely (fontFamily falls back to Amiri) — QCF's glyphs are whole pre-shaped words, so there's no way to recolor part of one letter-by-letter; this is an inherent trade-off of coloring by rule, not a bug to fix.
    - **Night Mode** (`lib/readingPrefs.js`): a reading-session dark override, independent of the app-wide theme in Pengaturan — someone can read in dark while the rest of the app stays light, or vice versa; it's `localStorage`-persisted separately, not derived from `ThemeProvider`. Implemented by overriding the same CSS custom properties (`--bg`, `--ink`, `--card`, etc.) that `theme.css` already defines on `:root`/`[data-theme]`, spread onto each page's outer `.screen` div — every `var(--token)` used anywhere in that subtree picks up the local override for free, no per-element styling needed. One real gotcha hit and documented in that file: `theme.css` sets `body { color: var(--ink) }`, which resolves once at body level using the *global* token and is what descendants inherit — simply overriding `--ink` deeper in the tree does NOT retroactively change that already-inherited `color`. `NIGHT_STYLE_VARS` has to re-declare `color: var(--ink)` itself so it re-resolves against the local override; shipping without that first made body text nearly invisible (dark-on-dark) while backgrounds/borders looked fine, since those happen to be set via their own explicit `var()` on each element rather than inherited.
    - **Decorative page frame + per-ayah action sheet (2026-08-29)**, built in this order per an explicit ask (action sheet first, frame second): (1) `AyahActionSheet` — tapping an ayah's number circle now opens a bottom sheet (murotal playback via the same `airmoon-qari` reciter preference already used in Mode Ayat, Indonesian translation, share/copy built from `text_uthmani` + translation + "QS. {surah} : {ayat}", and the existing last-read bookmark action) instead of bookmarking directly. (2) `PageFrame`/`SurahBanner`/`CornerOrnament` — a double-gold border around the whole page and a ribbon-shaped (`clip-path: polygon(0% 50%, 3% 0%, 97% 0%, 100% 50%, 97% 100%, 3% 100%)`) surah-name banner, after the founder pointed at a competitor Mushaf app's decorated page as a reference. The corner ornament went through real iteration: a first simple 2-ellipse "rosette" was correctly called out by the founder as too plain to be hand-drawn CSS (rightly suspecting the reference used a real downloadable asset); attempted to source a CC0 "Ornamental Islamic frame" from freesvg.org, but its download endpoint needed a real browser session that plain `curl` couldn't replicate — landed on an original geometric "strapwork" motif (nested right-angle bracket lines + a diamond accent) instead, matching the reference's *style* without tracing or downloading anyone else's actual file.
- **Qur'an word-level highlight — done, for 2 of 5 reciters, and this is the real ceiling, not a to-do.** `lib/quranTimingApi.js` pulls per-word timestamps from Quran.com's public API (`chapter_recitations/{id}/{surah}?segments=true` — free, no key, verified live) and `SurahReader.jsx` uses it to highlight the exact word as it's spoken (verified against real playback: highlight tracked one word for ~2s then correctly advanced to the next word/ayat). Only wired up for reciters with a clean 1:1 match to a Quran.com recitation — As-Sudais and Al-Afasy (`quranTimingApi.js`'s `hasWordSync`), flagged with a small badge in `PilihQari.jsx`. The other 3 EQuran.id reciters (Al-Juhany, Al-Qasim, and the one currently mislabeled "Al-Akhdar" — see the `quranApi.js` note below) keep the original whole-ayat highlight. This was re-investigated properly (not just re-checked against Quran.com again): Quran.com's `resources/recitations` list is genuinely capped at 12 reciters, none of which are these 3. EveryAyah.com/VerseByVerseQuran.com *does* publish timing files for Al-Juhany and Al-Qasim (`everyayah.com/data/timings_files/`) — but downloading and inspecting one (`Muhsin Al-Qasim_192kbps.zip` → `001.txt`) showed it's **ayah-boundary timing only** (8 numbers for Al-Fatihah's 7 ayat), not per-word segments — i.e. no better than the whole-ayat fallback this app already has. Don't wire that source in and call it "word sync" — it would show the "Highlight kata saat dibaca" badge for a feature it doesn't actually deliver. If a real per-word source for these 3 ever surfaces, it needs actual word-level segments (verified by inspecting the data, like this check did), not just "a timing file exists".
- **Adzan notifications — fully live now.** Real background push (works with the app closed) via FCM: `lib/notifications.js` registers `public/firebase-messaging-sw.js` and saves the token + location to `users/{uid}`; `api/send-prayer-notifications.js` (Firebase Admin, `FIREBASE_SERVICE_ACCOUNT_B64` already set in Vercel) checks due prayers per user via `/api/aladhan` and sends through FCM, deduped per prayer/day. `VITE_FCM_VAPID_KEY` is set in Vercel (Firebase Console → Cloud Messaging → Web Push certificates). The `CRON_SECRET` value that shipped originally was empty (a real misconfiguration — the endpoint always 401'd, not a security hole, since the check is `!process.env.CRON_SECRET || secret !== ...`) — replaced with a real generated secret; there's an external cron pinger on cron-job.org hitting `https://airmoon.vercel.app/api/send-prayer-notifications?secret=<CRON_SECRET>` every 5 minutes (Vercel's own Cron Jobs are daily-only on the Hobby plan, not fine-grained enough for 5x-daily prayer triggers).
  - **Gotcha that actually shipped broken once, worth knowing before it happens again**: `vercel env pull` silently returns an *empty string* for `VITE_FCM_VAPID_KEY` (and other vars — `GOOGLE_MAPS_API_KEY` too) even though `vercel env ls` shows them as set/"Encrypted" — reproduced repeatedly, not a one-off fluke. Building Firebase Hosting's static bundle with that empty value doesn't just ship a blank key: Vite/Rollup's dead-code elimination sees `if (!VAPID_KEY) throw ...` as the *only* reachable branch and strips the real `getToken()` call entirely, so the shipped function unconditionally throws "VAPID key belum diset" — this actually happened (caught 2026-08-28 while working on an unrelated fix, confirmed via a live-bundle diff against Vercel's own build, and fixed the same session by fetching the real value through a temporary authenticated Vercel serverless endpoint instead of a local pull). Vercel itself is never affected by this — `vercel --prod` triggers a build **on Vercel's own servers**, using its real dashboard env vars directly, completely ignoring whatever's in the local `dist` folder; only Firebase Hosting (which just uploads whatever static files it's handed, no server-side build step) is at risk. **Before ever trusting a local build for Firebase Hosting again, verify the built JS actually contains the real key** — grepping for the fallback error string is a fast check (0 matches = good, the throw-branch was proven unreachable and stripped instead).
  - **Notification body text rotates through 100 variants** (`api/_lib/prayerMessages.js`'s `PRAYER_MESSAGES` + `pickPrayerMessage()`), picked deterministically from `(date, prayer index)` so the exact same sentence isn't sent 5x/day forever and the 5 prayers on a given day don't repeat each other either — same day-of-year rotation idea as `data/headlines.js`.
  - **Fixed a real silent-notification bug (2026-08-29)**: each prayer reuses the same notification `tag` every day (`adzan-Isha`, `adzan-Subuh`, ...) so today's notification replaces yesterday's leftover instead of piling up in the notification center — but per the Notification API spec, replacing a same-tag notification is silent by default (no sound or vibration) unless `renotify: true` is set explicitly. Without it, a user only ever got a sound the very first time a given prayer's tag fired, then silent "updates" forever after. Confirmed this wasn't a phone-settings issue first (checked the reporting user's actual iOS notification-settings screenshot — Allow Notifications, Sounds, and Immediate Delivery were all already correctly enabled) before finding the real cause in `public/firebase-messaging-sw.js`.
- **Android TWA (`android-twa/`) notification delegation is enabled** (`enableNotifications: true` in `twa-manifest.json`, regenerated via `node scaffold.mjs`) now that the FCM backend above is live. **Not yet rebuilt into a new APK/AAB** — this needs `./gradlew bundleRelease` (or `assembleRelease`) run on a machine with a JDK + Android SDK installed, which this dev environment doesn't have. Regenerating via `scaffold.mjs` also re-fetches `iconUrl`/`maskableIconUrl` from the live site, so it's a good idea to re-run it (and rebuild) after any future logo/icon change too, not just for this notification flag. **Superseded for real notification sound** — see `android-native/` below; kept as-is for history, not actively developed further.
- **`android-native/` — a real native Android app (Kotlin), built 2026-08-31 specifically because the TWA above structurally cannot play a custom notification sound.** A TWA's notifications are still delegated through Chrome's own web-push display path — same ceiling the PWA/web version hit (see the Adzan notifications bullet's `renotify` note above): no API surface exists to attach a bundled sound file. `android-native/` is a genuinely different architecture: a full-screen WebView loading the same deployed `https://airmoon.vercel.app` (no UI duplicated), plus real Kotlin `FcmService.kt` (a `FirebaseMessagingService`) that builds every notification itself on a dedicated channel with a bundled sound file, instead of letting the OS auto-display it.
  - **Required the backend to switch to data-only FCM payloads** (`send-prayer-notifications.js`, `broadcast-doa.js`: title/body moved from the top-level `notification` field into `data`) — a `notification` payload gets auto-shown by the OS/browser using the default sound *before* any app code runs, on both web push and Android's native FCM, which would silently bypass the custom-sound channel entirely. `firebase-messaging-sw.js` (web) was updated to match, reading from `payload.data` now.
  - **Token bridge, no new backend code path**: `MainActivity.kt` tags the WebView's user agent with `AirmoonNativeApp/1.0` and hands the device's native FCM token to the page via `window.__airmoonNativeToken(token)`. `lib/notifications.js`'s `isNativeApp()` detects that tag and, inside `enablePrayerNotifications()`, waits for that bridged token instead of running the browser-only VAPID/`getToken()`/service-worker flow (none of which exist inside a plain WebView) — then saves it into the exact same `users/{uid}.fcmTokens` array a web token would use. `send-prayer-notifications.js`/`broadcast-doa.js` needed zero changes to also reach native devices; Admin SDK's `sendEachForMulticast` doesn't care whether a token is web-push or native FCM.
  - **External links (Google Forms, WhatsApp, Maps) are handed off to the system browser/app**, not loaded inside the WebView (`MainActivity.kt`'s `shouldOverrideUrlLoading`, checked against an explicit allow-list of the app's own hosts) — Google Forms' file-upload question fails inside embedded WebViews the same way it was diagnosed failing inside WhatsApp's in-app browser (2026-08-30), so this avoids reintroducing that exact bug inside the native app.
  - **4 azan sounds to pick between, matching `pages/PilihAdzan.jsx`'s web list exactly** (`AzanSound.kt`) — deliberately the same 4 labels as that older, web-only picker: Makkah (`res/raw/azan_makkah.mp3`, 4:43, "Makkah Azan-Ramadan" from a dedicated Haramain-recordings Internet Archive account, CC0), Madinah (`res/raw/azan_madinah.mp3`, 1:08, trimmed+faded from a CC0 live Masjid Nabawi Fajr recording — trimming is a permitted derivative use under CC0), Mishary Rasyid (`res/raw/azan_mishary_placeholder.mp3` — **not actually his voice**; searched for a licensed al-Afasy recording and found none, unlike the live-broadcast Makkah/Madinah recordings a named reciter's studio recording is a different, much-less-likely-to-be-free case — currently a copy of the generic clip as a stand-in, swap in a real one if the founder has rights to one), and Nada Pengingat (`res/raw/beep.mp3`, a locally-generated two-tone chime, no azan/licensing question at all — matches the web picker's "tanpa suara adzan, cuma beep" option). Each gets its own permanent notification channel (a channel's sound is locked in at creation, so a picker needs one channel per option); `FcmService.onMessageReceived` reads the currently-saved choice (`SharedPreferences`, default Makkah) fresh on every notification.
  - **`pages/PilihAdzan.jsx`'s web "Suara Azan" picker is cosmetic-only, confirmed by grep** — its selection (`localStorage['airmoon-adzan-sound']`) is read only by itself and by `JadwalSholat.jsx` (just to display the current label), never by any backend/service-worker code that could act on it. It predates this session's native-app work and was likely built without realizing the Web Notification API has no mechanism to attach a custom sound at all — so regardless of which of its 4 options someone picks, real push notifications on web/PWA have only ever played the browser's default sound. Its 14s preview clips (`public/adzan-preview/*.mp3`, sourced from `github.com/achaudhry/adhan`, an unlicensed hobby repo) were left as-is (out of scope, preview-only use); the native app's bundled files above deliberately did NOT reuse that same source for anything beyond the Mishary Rasyid label/placeholder situation described above, precisely because that repo has no stated license.
  - The web app's Pengaturan page renders a "Suara Azan" picker (`AzanSoundPicker` in `Pengaturan.jsx`) that only appears inside the native shell (`isNativeApp()`) and talks to `window.AndroidBridge`'s `get/setAzanSound()` — this is the one place a selection actually controls real playback; a regular browser/PWA has nothing to pick between since it can't attach a custom sound at all.
  - **No local build here either** — same missing JDK/Android SDK gap as the TWA above. `.github/workflows/android-build.yml` builds a debug `.apk` on GitHub's own runners instead (on push under `android-native/`, or manual `workflow_dispatch`), downloadable from the run's Artifacts — no Android Studio needed anywhere. **Needs a `GOOGLE_SERVICES_JSON_B64` repo secret before it can succeed** (base64 of a `google-services.json` from registering a new Android app — package `id.web.jalanmenujusurga.app` — in the `airmoon-d9620` Firebase project; exact steps in the README) — a founder-only step needing Firebase Console access this environment doesn't have. The very first push of `android-native/` will show a red/failed run in Actions until that secret is added — expected, not a sign anything is broken.

## Design decisions already settled

These came out of iteration with the founder — keep them unless explicitly asked to change:

- **Palette**: dark teal `#0d4d47` / `#0a3630` (primary), gold `#e8b84b` (accent), white `#ffffff` background, pastel tint cards (mint `#e2f1ec`, cream-gold `#fbf0d9`) for stat/service tiles. **Dark theme redesigned 2026-08-29** — was a bright neon mint `#6ee7c9`, which doubles as both small icon/nav-active text colors *and* the big gradient hero-card backgrounds that have hardcoded white text on top (Home's Jadwal Sholat card and its equivalents on SurahList/JadwalSholat/KutipanInspirasi/ModeRamadan/KalkulatorZakat) — that bright value made those cards look like a glowing neon-green screen instead of matching light mode's actual dark-teal/gold brand look, called out directly by the founder ("dark mode ijonya jelek bgt bikin sakit mata"). Replaced with a muted bronze-gold `#a8823c` / `#6b4f22` pair on a warm near-black `#0b0c0a` (warmed off the old green-black `#071612`/minty-white `#f4faf7`, to `#f4f0e6` ivory) — dark enough for the same hardcoded-white-text cards to stay legible while still popping against the background. `--success` was also decoupled into its own calmer green `#4fbf82` (previously an exact alias of `--primary`, which was part of what made dark mode read as green everywhere) — see `app/src/styles/theme.css` for the full token set (`[data-theme='dark']`).
- **Type**: Poppins (Google Fonts) for UI text, Amiri for Arabic verse/dua text. The **logo wordmark specifically** uses Fredoka (`components/Logo.jsx`) to match the founder's reference deck's rounded wordmark more closely than Poppins did — Fredoka is not used anywhere else.
- **Logo mark**: a solid filled crescent (no stroke, no circle badge behind it) plus a real 5-point star sitting in the crescent's own inner notch — see `components/Logo.jsx`. This replaced an earlier outline-crescent + 4-point-sparkle version after the founder shared the actual design-system asset pack (`Moon (airmoon) Design System.zip`) showing the mark is meant to be solid-filled; the star's exact position/size was traced from that reference PNG via pixel connected-component analysis, not eyeballed. The mark's viewBox is intentionally tight around the shape (`2.921 3.271 17.801 17.801`, not `0 0 24 24`) so it renders larger within the same `size` prop — don't "fix" that back to a square 0-24 viewBox. Same path + viewBox duplicated in `index.html`'s inline favicon data-URI; keep both in sync if either changes.
  - **Construction: a single connected SVG path, not a mask.** The crescent is one outer circle arc (R=8.5) and one inner "bite" circle arc (R=6) sharing two real endpoints — `M{p1} A8.5,8.5 0 1,0 {p2} A6,6 0 1,1 {p1} Z`. This went through several broken constructions before landing here, worth knowing before touching the geometry again: (1) two full circles each drawn as two 180°-apart arcs combined via `fill-rule="evenodd"` — the diametrically-opposite arc endpoints have a genuinely ambiguous large-arc-flag, which produced a stray thin sliver in production; (2) real `<circle>` elements combined via a `<mask>` with React's `useId()` for the mask id — worked in Chromium but Safari/WebKit fails to resolve `url(#:r0:)` (colon-containing ids from `useId()`) and silently skips the mask, rendering the raw unmasked outer circle as a plain solid circle (only caught because the founder checks on an actual iPhone, not from any tool in this environment); (3) the mask geometry itself had the inner "bite" circle fully contained within the outer one (margin as small as 0.15 units) rather than genuinely poking past its edge — this doesn't error, but it means the crescent never actually opens, it just tapers to a very thin sliver that still wraps almost all the way around, reading as a solid ball/donut at icon size, which is a real design defect independent of the rendering-engine bugs above. The current path's two arc endpoints are ~50-74° apart on each circle (nowhere near the 180° ambiguous case) and the bite circle genuinely intersects the outer one (no containment), so there's no mask, no dynamic id, and no fill-rule to go wrong — verified via canvas pixel connected-component scan (exactly 2 regions: crescent + star, unfiltered by region size, since an early verification pass with a size filter is what let bug (1) slip through once already) plus a live-vs-local `/assets/*.js` and PNG-hash check on both hosts. If the shape ever needs adjusting again (fatter, thinner, different tip gap), regenerate the two circles' center/radius/offset so they still genuinely intersect and re-derive the path's endpoints from actual circle-circle intersection math — don't hand-tune the `A` command's radii/flags directly.
  - **App icon PNGs** (`public/icons/icon-192.png`, `icon-512.png`, `maskable-192.png`, `maskable-512.png`, `apple-touch-icon.png`) are rasterized from this same crescent+star path via `rsvg-convert` — they don't update automatically when `Logo.jsx`'s geometry changes, so any future shape tweak needs the PNGs regenerated and redeployed too, or the home-screen icon and in-app logo will silently drift apart (this already happened once — it's what made the "circle" bug look fixed in-app while the iOS home screen icon was still the old broken shape). `icon-192`/`icon-512`/`apple-touch-icon` are plain squares with the mark filling ~72% of the canvas (OS applies its own corner rounding); the two `maskable-*` ones use the same square but with the mark scaled down to ~59% of the canvas, per the maskable-icon safe-zone convention. iOS also caches whatever `apple-touch-icon.png` looked like at the moment a user did "Add to Home Screen" and won't refetch it later — a founder/user still seeing the old icon after a redeploy usually just needs to remove and re-add the home screen shortcut, not a sign the deploy failed.
- **Icons**: inline SVG line icons for nav/UI chrome, including all 4 Home "Layanan" tiles now (Qur'an/Kiblat/Cari Masjid/Sholat — see `components/serviceIcons.jsx`'s `QuranBookIcon`/`QiblaCompassIcon`/`MosqueIcon`/`PrayerClockIcon`). This grid used to be a deliberate emoji exception (📖🕌🤲🕋, per an explicit "make them look less flat/cheap" ask) before the founder later asked for custom icons here too, same reasoning as the Lainnya grid's icon pass (2026-09-01/02) — don't reintroduce emoji on this row without checking first, the exception is gone.
- **Bottom nav**: a floating rounded pill, not a full-width bar. Items: Home, Qur'an, Donasi, Umroh Needs, **Lainnya** (added 2026-09-03 as a 5th tab — see the BottomNav rework note above; the original 4 stayed as-is, this wasn't a replacement). **Rendered via `createPortal(..., document.body)` since 2026-09-04**, not as a plain child of `.screen` — a reported bug (the pill floating up and getting stuck mid-screen, blocking content) traced to `position: fixed` needing zero transformed/filtered/`will-change`/`contain`-ed ancestors to resolve against the true viewport; `.screen` has picked up new CSS multiple times this session and could again, so BottomNav rendering as its child was one future edit away from silently reintroducing this. A scratch repro (transformed ancestor + tall scrollable content) confirmed the exact failure mode before landing the fix. Don't move BottomNav back to rendering inline under `.screen` without re-litigating this.
- **Visual reference**: `Deck/Moon - Sequoia .pdf` (outside this repo) — the teal/gold palette, arabesque line-pattern accents, and card-based layout are intentionally derived from this deck, not invented fresh.
